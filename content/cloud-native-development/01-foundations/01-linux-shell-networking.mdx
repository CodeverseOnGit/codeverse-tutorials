## Why this chapter exists

Every cloud native tool you'll touch — Docker, Kubernetes, CI runners — is a thin
wrapper around Linux primitives that have existed for decades. `docker run` is not
just magic; it's namespaces, cgroups, and a filesystem overlay, all Linux kernel
features. A Kubernetes Pod isn't magic either; it's a group of containers sharing
a network namespace.

When a container mysteriously can't reach another service, or a pod gets OOMKilled,
or a Helm chart deploys but nothing responds on the expected port — the debugging 
skill you reach for is not "read the Kubernetes docs harder." It's "check what's
actually listening, what the DNS resolves to, what the process is
doing." That skill is Linux and networking fundamentals. Skip this
chapter and you'll spend the rest of this path debugging blind.

## What you'll be able to do after this chapter
 
- Navigate and inspect a Linux system confidently from the shell
- Understand processes, users, permissions, and how they relate to
  container security later
- Read and reason about basic networking: IP addresses, ports, DNS,
  and how a request actually travels from client to server
- Use core diagnostic commands you'll reach for constantly in every
  later module: `ps`, `top`/`htop`, `ss`, `curl`, `dig`, `journalctl`

## 1. The shell is not optional
 
Every cloud provider console, every Kubernetes dashboard, every GUI
tool eventually breaks down to "just SSH in and look." The command
line isn't a beginner's on-ramp you graduate out of — professional
cloud native engineers live in it daily. A few non-negotiable habits
worth building now:
 
- Prefer typing commands over clicking through GUIs, even when the GUI
  exists — muscle memory here compounds for years.
- Learn to read `man` pages and `--help` output instead of immediately
  searching the web. It's faster once you're used to it, and it works
  offline (e.g. inside a container with no internet).
- Get comfortable with `bash` scripting basics — if you find yourself
  running the same 3 commands repeatedly, that's a script.


### Core navigation and file commands
 
```bash
pwd                     # print working directory
ls -la                  # list files, including hidden ones, with details
cd /var/log             # change directory
cat access.log          # print a file's contents
less access.log         # scroll through a large file
tail -f access.log      # follow a file live as it's written to (huge for debugging)
grep "ERROR" access.log # search for a pattern in a file
find / -name "*.conf"   # find files by name across the filesystem
```

`tail -f` deserves special attention — you will use this exact pattern
constantly, just swapped for `kubectl logs -f` later. It's the same
mental model: "show me what's happening right now."

## 2. Processes: what's actually running
 
A Linux system is fundamentally a set of running processes, each with
a PID (process ID), competing for CPU, memory, and I/O. Containers
later will just be processes with extra isolation — so understanding
"what is a process" now makes "what is a container" trivial later.
 
```bash
ps aux                  # list all running processes
top                      # live view of process resource usage
htop                     # a nicer, interactive version of top (install if missing)
kill -9 <PID>            # forcibly terminate a process
```
 
Try this: open two terminal windows. In one, run a command that hangs
(`sleep 300`). In the other, find its PID with `ps aux | grep sleep`
and kill it. This exact loop — "something is misbehaving, find it,
kill it" — is what you'll do to a stuck container or pod later,
just with `docker kill` or `kubectl delete pod`.

## 3. Users, permissions, and why "it works on my machine" often means "as root"
 
Linux permissions follow a simple but easy-to-misunderstand model:
every file has an owner, a group, and permission bits for
read/write/execute, separately for owner/group/everyone else.
 
```bash
ls -l app.py
# -rwxr-xr-- 1 alice developers 1240 Jan 3 10:00 app.py
```
 
Reading that: owner `alice` can read/write/execute(rwx), the `developers`
group can read/execute(r-x), everyone else can only read(r--).
 
```bash
chmod +x script.sh       # make a file executable
chown alice:developers app.py   # change owner and group
sudo <command>            # run a command as root (superuser)
```

**Why this matters for later chapters**: a huge class of container
security issues comes from running processes as root inside a
container unnecessarily. When you get to Module 8 (DevSecOps) and see
guidance like "don't run containers as root," this is the exact
concept it's building on — Linux permission boundaries, just applied
inside a container's isolated view of the filesystem.

## 4. Networking: how a request actually gets somewhere
 
This is the part most tutorials rush, and it's the part that will
save you the most debugging time later. A few layered concepts:
 
**IP addresses and ports.** Every machine on a network has an IP
address; every service on that machine listens on a specific port.
`192.168.1.10:8080` means "port 8080 on the machine at that IP."
 
**DNS.** Humans use names (`google.com`), machines use IPs. DNS is the
system that translates one into the other. Later, Kubernetes has its
own internal DNS system (CoreDNS) that lets pods find each other by
service name instead of IP — same underlying idea.
 
**TCP vs UDP, briefly.** TCP is reliable and ordered (used for HTTP,
most APIs); UDP is fast but unordered and can drop packets (used for
DNS queries themselves, video streaming, some gaming). You don't need
deep protocol knowledge yet — just know these are different transport
guarantees.

### Commands you'll use constantly
 
```bash
ip addr                 # show this machine's network interfaces and IPs
ss -tulpn               # show what's listening on which ports (modern netstat)
ping google.com          # check basic connectivity and latency
curl -v https://example.com   # make an HTTP request, -v shows the full exchange
dig example.com          # query DNS directly, see the resolution
traceroute example.com   # see the network hops a packet takes to its destination
```

Try `curl -v` against a real site and actually read the output — you
will see the DNS resolution, the TCP handshake, the TLS handshake, the
HTTP request headers, and the response headers, all in one command.
This is the entire request lifecycle you'll be debugging inside
containers and Kubernetes clusters for the rest of this path.

## 5. Putting it together: a mini investigation
 
Here's a scenario you'll hit constantly, condensed into an exercise:
"a service isn't responding, what do I check?"
 
```bash
# 1. Is anything even listening on the expected port?
ss -tulpn | grep 8080
 
# 2. Is the process actually running?
ps aux | grep myapp
 
# 3. Can I reach it locally?
curl -v http://localhost:8080/health
 
# 4. If not locally, is it a DNS problem?
dig myapp.internal
 
# 5. Check recent logs for errors
journalctl -u myapp --since "10 minutes ago"
```

This five-step sequence — listening check, process check, local
reachability, DNS, logs — is the exact debugging flow you'll reuse
with `kubectl get pods`, `kubectl exec`, `kubectl logs`, and
`kubectl describe service` in Module 3. Learning it here, against a
plain Linux box with no Kubernetes complexity layered on top, makes it
far easier to reason about later.


## Try it yourself
 
Set up a throwaway Linux environment (a cloud VM, a local VM, or WSL
on Windows) and complete this checklist:
 
- [ ] Navigate the filesystem using only the shell for 30 minutes — no GUI file manager
- [ ] Start a background process, find its PID, and kill it
- [ ] Create a file, change its permissions so only you can execute it, then run it
- [ ] Run `curl -v` against three different websites and identify the DNS, TCP, and HTTP portions of the output
- [ ] Use `ss -tulpn` to find every port currently listening on your machine, and identify what's using each one

### Answer key
 
1. b — `ss -tulpn` lists listening sockets with process info.
2. c — `chmod +x` adds the execute permission bit.
3. b — DNS resolves human-readable names to IP addresses.
4. b — both are "follow the live output" patterns for logs.
5. b — always confirm the process/port is actually listening before assuming anything else is broken.
6. b — the `r-x` in the group segment means the group can read and execute, alongside the owner's `rwx`.
7. b — container root is still Linux root under the hood; the same privilege risks apply, just inside a more isolated filesystem view.
